# Пайплайны-примеры

Три готовых пайплайна на новые блоки конструктора. Каждый — выгрузка из самого дашборда, так что
импортируется обратно без правок.

| Файл | Что показывает |
|---|---|
| `review-loop.pipeline.json` | **Цикл с промптом.** Один блок на 5 итераций с промптом «проведи ревью, после поправь ошибки», затем шаг-отчёт. Тело живёт в промпте: рёбер рисовать не надо. |
| `loop-region.pipeline.json` | **Цикл-регион.** «Цикл» на 3 итерации → прогнать тесты → починить упавшее → «Конец цикла». Возврат в начало делает сервер, обратного провода на полотне нет. Выход по лимиту уходит на отчёт. |
| `orchestrator.pipeline.json` | **Оркестратор.** «Оркестратор» (2 попытки на шаг) → собрать факты → черновик → вычитка → «Приёмка» → выводы. У шагов внутри региона стоит подсказка «кому»: два «подешевле» и одна «средняя»; шаг после приёмки директор делает сам. |

## Импорт

```bash
curl -fsS -X POST http://localhost:8080/api/pipelines/import \
  -H 'Content-Type: application/json' \
  --data @docs/examples/pipelines/review-loop.pipeline.json
```

Нужен включённый экспериментальный флаг «Pipelines» в Настройках дашборда. Если slug уже занят,
импорт не падает, а создаёт копию с суффиксом (`review-loop-2`) — ответ говорит, какой slug вышел.

После импорта пайплайн открывается в конструкторе как обычный и запускается обычным «запусти
пайплайн «Ревью в цикле»» — исполняет его агент по скиллу `pipelines`.

## Чего в примерах нет

Файлы экспорта не содержат загруженных `.md`-файлов (в формате их нет вовсе) — в этих трёх примерах
их и не используется. Токены проводов данных на импорте перегенерируются, поэтому в промптах
`{{data:...}}` после импорта будут другие идентификаторы — это нормально и видно в конструкторе как
те же самые провода.
