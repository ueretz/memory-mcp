# Плашка входа: переменные перестают быть шагами, старт становится явным

Дата: 2026-11-09

## Зачем

Сегодня «Переменная» — это шаг (`PipelineStep.ContentType.VARIABLE`). Из этого следует всё
остальное: у неё есть переход «далее», она обязана стоять в цепочке переходов, а значит
автор пайплайна вынужден **выстраивать переменные в линию** — старт → `var1` → `var2` → `var3` →
первый настоящий шаг. Если одна переменная должна собираться из другой, её тоже приходится
втыкать шагом.

Две конкретные проблемы:

1. **Переменная не является действием.** Она ничего не делает в ходе выполнения — это
   константа. Её присутствие в графе переходов — ложь о порядке исполнения.
2. **Она занимает место.** Каждая переменная — полноценная карточка 320px шириной в цепочке.
   Пять переменных съедают пол-экрана и ломают читаемость графа.

Параметры запуска этой проблемы не имеют: они живут на отдельной фиксированной плашке
(`PipelineParamsNode`) с пином на каждый параметр и подключаются проводом данных туда, где нужны.
Переменная — ровно того же рода сущность. Она должна жить там же.

Заодно решается смежная кривизна: **старт пайплайна сегодня выводится, а не задаётся.**
Стартовый шаг — это «тот, у кого нет входящих переходов», и из этого рождаются два
диагностических сообщения, которые автор видит чаще всего: «Нет стартового блока» и «Несколько
стартовых блоков». Оба — следствие вывода. Когда переменные уходят из графа, большая часть
ложных «нескольких стартов» исчезает сама, но сам вывод остаётся хрупким. Старт становится
явным выходом плашки входа.

## Что получается

Одна фиксированная плашка **«Вход пайплайна»** вместо нынешней «Параметры запуска», с тремя
секциями:

```
┌─ Вход пайплайна ──────────────── ⚙ ─┐
│  Старт                           ●──┼──→ первый шаг   (переход, серый)
├─────────────────────────────────────┤
│  Параметры запуска                  │
│  mr_url            текст        ○───┼──→ данные        (жёлтый/синий/сиреневый по типу)
│  threshold *       число        ○───┤
├─────────────────────────────────────┤
│  Переменные                      +  │
│  ○──┼ reviewer     @ivan        ○───┼──→ данные        (бирюзовый)
│  ○──┼ greeting     Привет, {{…}} ○──┤
└─────────────────────────────────────┘
```

- **Старт** — один переход (flow) наружу. Куда он подключён, оттуда пайплайн и начинается.
- **Параметры** — как сегодня: значение вводит пользователь при запуске, пин отдаёт его в шаг.
- **Переменные** — имя + значение, редактируются прямо на плашке. Справа пин-источник (отдать
  значение в шаг или в другую переменную), слева пин-приёмник (собрать значение из параметра или
  другой переменной).

Переменная больше не шаг: у неё нет перехода «далее», её нельзя поставить в цепочку, она не
участвует в достижимости и не может быть стартом.

## Цели

- Переменная подключается проводом данных и не занимает места в графе переходов.
- Переменная может собираться из параметра и из другой переменной — без шагов.
- Старт пайплайна задаётся явно, а не выводится из входящих степеней.
- Существующие пайплайны с `VARIABLE`-шагами переезжают сами, без ручной переделки.
- Существующие запуски (`pipeline_run_steps`) остаются читаемыми: история не переписывается.

## Не цели

- Типы у переменных (`STRING`/`NUMBER`/`BOOLEAN`, как у параметров). Переменная — текст; если
  понадобится сравнивать как число, это задача шага «Условие», а не переменной.
- Переменные, меняющиеся в ходе выполнения (счётчики, аккумуляторы). Переменная здесь —
  константа времени сборки, разворачиваемая один раз на старте запуска.
- Переменные уровня проекта / глобальные, общие для нескольких пайплайнов.
- Несколько стартов (параллельный запуск нескольких ветвей с нуля). Старт ровно один.

## Анти-цели

Чего не должно случиться, даже если формально всё заработает:

- **История запусков не должна поехать.** `pipeline_run_steps` старых запусков содержат строки с
  `content_type = 'VARIABLE'`. Их CHECK-ограничение обязано продолжать принимать это значение, а
  экран запуска — рисовать такой шаг без падения.
- **Миграция не должна порвать граф.** Если `VARIABLE`-шаг стоял в середине цепочки
  (`A → var → B`), после миграции должно остаться `A → B`, а не два обрубка.
- **Плашка не должна превратиться во второй редактор пайплайна.** Это вход: старт, параметры,
  переменные. Никакой логики, условий и ветвления на ней не появляется.

## Решения по реализации

### Схема (миграция V24)

```sql
CREATE TABLE pipeline_variables (
    id BIGSERIAL PRIMARY KEY,
    pipeline_id BIGINT NOT NULL REFERENCES pipelines (id) ON DELETE CASCADE,
    order_index INT NOT NULL,
    name VARCHAR(100) NOT NULL,
    value TEXT,
    UNIQUE (pipeline_id, name)
);
```

`pipeline_data_links` получает `source_variable_id BIGINT REFERENCES pipeline_variables (id) ON
DELETE CASCADE`, а `pipeline_data_links_source_check` переписывается на «ровно один из трёх
источников»: шаг+выход, параметр, переменная.

Цель провода тоже расширяется: сегодня `target_step_id NOT NULL`, а провод в переменную целится
не в шаг. Добавляется `target_variable_id`, `target_step_id` становится nullable, и CHECK требует
ровно одну цель.

`pipelines` получает `start_step_id BIGINT REFERENCES pipeline_steps (id) ON DELETE SET NULL`.

`pipeline_steps.content_type` CHECK теряет `'VARIABLE'`; `pipeline_run_steps.content_type`
CHECK **сохраняет** его — ради истории.

### Переезд существующих данных (та же миграция)

Для каждого `VARIABLE`-шага:

1. Создать `pipeline_variables` (`name` = `title`, с приведением к уникальности в рамках
   пайплайна; `value` = `prompt_text`; `order_index` по `order_index` шага).
2. Провода, выходившие из его выхода, перевести на `source_variable_id`.
3. Обойти его в графе: цели маршрутов, ведущих в него, переставить на цель его маршрута «далее»
   (а если такого нет — маршруты удалить).
4. Удалить шаг (каскадом уйдут его выходы и маршруты).

`start_step_id` для каждого пайплайна проставить выведенным сегодня корнем — шагом без входящих
маршрутов с наименьшим `order_index` (после выноса переменных).

Если имя шага-переменной пустое или не уникально, имя переменной получает суффикс (`value`,
`value_2`) — молча, с предупреждением в логе миграции не обойтись, поэтому имя остаётся
читаемым и автор поправит его на плашке.

### API

`PipelineUpsertRequest` получает:

- `List<VariableRequest> variables` — `(name, value)`;
- `List<VariableLinkRequest> variableLinks` — `(token, variableName, targetStepIndex,
  targetVariableName)`, ровно одна из двух целей;
- `Integer startStepIndex`.

Как и `parameterLinks`, провода переменных живут на верхнем уровне, а не внутри шага: их
источник — не шаг. Все новые поля добавляются через компактный конструктор с дефолтами, а старая
форма записи сохраняется перегруженным конструктором — ровно так, как это сделано для
`parameterLinks` (pre-V17) и watcher-полей (pre-V22). Экспорт (`PipelineExportService`) ходит
через `PipelineUpsertRequest`, поэтому новые поля подхватываются им автоматически; перегенерацию
токенов при импорте нужно распространить на `variableLinks`.

`PipelineDetail` получает `variables`, `variableLinks` и `startStepOrderIndex`.

### Валидация (`PipelineService`)

Уходит: «Pipeline has no starting step» / «more than one starting step» как следствие вывода.
Приходит:

- `startStepIndex` обязателен, когда шагов больше нуля, и должен указывать на существующий шаг;
- шаги, недостижимые от старта, — предупреждение на доске (не ошибка сохранения), как сегодня;
- имя переменной: непустое, уникальное в пайплайне, по форме как имя параметра;
- провода между переменными не должны образовывать цикл (`a → b → a`);
- переменная обязана иметь значение **или** входящий провод — пустая переменная без источника
  это ошибка.

Правило «данные идут только по ходу выполнения» (источник должен быть предком цели) к переменным
не применяется: переменная разворачивается на старте и доступна любому шагу — ровно как параметр.

### Выполнение (`PipelineRunService`)

`executeVariableStep` исчезает вместе с ветвью `case VARIABLE`. Вместо него на старте запуска
значения переменных разворачиваются один раз: топологический проход по проводам между
переменными, подстановка `{{data:<token>}}` из параметров и уже развёрнутых переменных.
Развёрнутые значения кладутся туда же, откуда их берёт подстановка в шагах, — тем же путём, что
значения параметров.

Старт запуска берёт `start_step_id` вместо `resolveRootOrderIndex`; вывод остаётся только как
запасной путь для пайплайнов, у которых `start_step_id` почему-то пуст.

### Доска (`PipelineBoardView`, `PipelineParamsNode` → `PipelineInputNode`)

`VARIABLE` уходит из `BLOCK_KINDS` — его больше нельзя положить на доску как блок.
`BoardStep`-часть модели переменных заменяется на `BoardVariable` (`name`, `value`) и
`BoardVariableLink`, по образцу `BoardParamLink`.

Плашка входа рисует три секции и отдаёт три вида пинов: `start-out` (flow), `param-out-<i>`
(данные, как сегодня), `var-out-<i>` / `var-in-<i>` (данные). Провод `start-out → шаг` пишет
`startStepIndex`.

Диагностика на доске (`collectIssues`) переписывается под явный старт: «старт не подключён»
вместо «нет стартового блока» и «несколько стартовых блоков».

### Что остаётся исполнителю на усмотрение

- Как именно разложить три секции плашки, чтобы она не выросла: сворачивать ли секцию переменных,
  когда их много, и где держать кнопку «+ Переменная».
- Формат имени переменной в токене подстановки (`{{var:name}}` против нынешнего
  `{{data:<uuid>}}`): провода уже дают уникальный токен, так что менять синтаксис не обязательно —
  решение за реализацией, лишь бы редактирование имени переменной не ломало существующие провода.
- Нужен ли переменной отдельный цвет пина или достаточно бирюзового из нынешней `BLOCK_KINDS`.
